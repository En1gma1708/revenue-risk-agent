Fix get_subscription_status() to handle real subscription states

Found live while actually exercising the Subscriptions API for the first time (account
activation was resolved, then create_test_plan_and_subscription() was run for real against a
genuine test subscription): the status map only covered pending/halted/active, so a freshly
created subscription (real status "created", before mandate authorization) silently returned
None instead of a sensible mapping. Added "created" and "authenticated" -> PENDING (both mean
"mandate not yet active, no charge has failed yet," matching this project's own PENDING
semantics). cancelled/completed/expired correctly stay unmapped -- genuinely outside this
project's 3-state guardrail model, not force-mapped to something misleading.

Also attempted the real pending->halted mandate walk via Playwright browser automation against
the live test checkout flow (claude-in-chrome wasn't available this session). Made real progress
(contact details, card entry, reaching the OTP/mandate-authorization step) but hit a genuine
external rate-limit on OTP verification attempts, tied to the test phone number/session rather
than a wrong OTP value -- confirmed by hitting the same limit on a completely fresh subscription.
Stopped deliberately rather than keep retrying against real infrastructure. Full detail in
DEVLOG.md (gitignored). Two real test-mode subscriptions now exist on the account
(sub_TWKVUdPbb5IJBX, sub_TWLxw70THfygjQ), both stuck pre-authorization.
